# 78. 프로젝트 1 · 상용 서비스 클론 — 미션 예시

> 팀 회차 — 혼자 하는 학습자용 버전

## 배우기 재료
- 핵심 개념
  - **먼저 똑같이, 그다음 더 낫게**: 핵심 흐름 하나를 원본과 **똑같이** 클론한 뒤(흐름 닮음), 분석에서 찾은 문제 1~2개만 고쳐 "개선 전(클론) → 개선 후"를 비교해요. 똑같이 만들어 봐야 원본이 왜 그렇게 만들었는지 보이고, 개선도 근거가 생겨요.
  - **범위는 핵심 흐름 하나**: 서비스 지도(`site.flows`)에서 흐름 하나, 화면 3~4개(예: 홈 → 목록(거르기) → 상세 → 찜·담기)를 골라요. 로그인이 필요한 단계는 내가 직접 로그인해 본 화면을 보고 화면만 만들어요. 결제는 결제 직전 화면까지 만들고, 원하면 선택 미션으로 테스트 결제를 붙여요.
  - **클론은 복사가 아니에요**: 원본의 로고·사진·글은 쓰지 않아요. 가상의 이름·로고, 내가 쓴 글, 자리 표시 사진을 쓰고, 푸터와 README 에 "교육용 클론 — 원본: (사이트 이름)"을 적어요.
- 작은 따라 치기 (사이트와 상관없이 직접 쳐요. 분석표 한 줄을 `docs/analysis.md` 에 써 봐요)
  ```markdown
  | 화면 | 사용자 목표 | 첫눈에 보이는 것 | 불편한 점(근거: 캡처 번호) | 개선 아이디어 |
  |---|---|---|---|---|
  | 목록 | 마음에 드는 것 거르기 | 큰 사진 카드 | 거르기 버튼을 못 찾음 (캡처 2) | 거르기 버튼을 위로 |
  ```
- 예상해 보기: 분석표에서 "불편한 점"에 캡처 번호나 인터뷰 말을 안 적으면 발표 때 무엇이 문제일까요? — 답: 근거가 없어서 "내 느낌"이 돼요. 평가에서도 기획력은 근거 → 문제 → 개선안이 이어지는지로 봐요.

## 원본 닮음
미션마다 완료 기준 끝에 "원본 닮음" 기준을 하나 더한다. 튜터가 고른 사이트를 같은 폭으로 열어 아래 항목의 **원본 값**(칸 수·순서·자리·DevTools로 읽은 값)을 넣어 구체적으로 만든다. 사진·글은 원본 것을 쓰지 않으므로 비교하지 않는다.
- PJ1-1: 분석표의 화면·단계가 서비스 지도의 그 흐름과 같고, Figma 프레임이 원본 화면 배치와 같음
- PJ1-2: 흐름 닮음: 원본과 같은 순서로 눌러 단계마다 화면 배치·주소 모양·상태가 같음 (로그인 뒤 단계는 화면만)
- PJ1-3: 바꾼 곳 1~2개 말고는 PJ1-2 클론(원본)과 같음, 개선 전·후 비교 표가 있음
- PJ1-4: 해당 없음 (테스트 결제 — 결제 직전 화면까지는 PJ1-2 에서 원본과 같게)

## 선택 미션 PJ1-4 참고 (토스페이먼츠 공식 문서, 2026-11-25 확인)
- 테스트 환경에서는 결제가 승인돼도 실제로 돈이 나가지 않아요 — [환경 설정하기](https://docs.tosspayments.com/guides/v2/get-started/environment)
- 이메일로 회원가입하면 개발자센터에서 테스트 키를 볼 수 있어요. 전자결제 신청 전에는 "개발 연동 체험 상점"의 일부 테스트 키만 보여요 — [API 키](https://docs.tosspayments.com/reference/using-api/api-keys)
- 시크릿 키는 클라이언트·GitHub 에 노출되면 안 돼요. 승인 API 는 시크릿 키 뒤에 `:` 를 붙여 base64 로 인코딩한 값을 `Authorization` 헤더(Basic 인증)에 넣어요 — [인증](https://docs.tosspayments.com/reference/using-api/authorization)
- 결제 요청 후 10분 안에 승인해야 해요. 요청 전에 `orderId`·`amount` 를 서버에 저장해 두고 승인 때 비교해요 — [결제위젯 연동](https://docs.tosspayments.com/guides/v2/payment-widget/integration)

## 힌트 재료
- 1단계: Next.js 배포 — https://nextjs.org/docs/app/getting-started/deploying , GitHub Docs README — https://docs.github.com/ko/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes
- 2단계: 분석은 화면 하나씩 "사용자 목표 → 불편한 점 → 근거" 순서로 적어요. 구현은 공통(레이아웃·공통 컴포넌트·데이터)을 먼저, 개선 포인트가 드러나는 화면을 그다음에 만들어요. 배포는 마지막 날이 아니라 일찍 연결해 둬요. 발표 자료는 한 장에 메시지 하나, 캡처·숫자로 보여 줘요.
- 3단계 예시(다른 이름·다른 값):
  ```markdown
  # 책갈피 (교육용 클론 — 원본: ○○서점)
  - 배포 주소: https://example.vercel.app
  - 개선 포인트: 목록 위에 거르기 버튼을 두었어요 (분석표 캡처 2)
  - 원본과 다른 점: 가상 이름, 내가 쓴 글, 자리 표시 사진
  - 출처: 자리 표시 사진은 직접 만든 그림
  ```

## 자주 막히는 곳
- 범위가 끝나지 않음 → 화면 3~4개, 핵심 흐름 하나로 줄여요. 시간이 남으면 선택 기능을 넣어요
- 처음부터 고쳐서 만듦 → PJ1-2 는 원본과 **똑같이**가 기준이에요. 고칠 점은 메모만 해 두고 PJ1-3 에서 반영해요
- 시크릿 키를 브라우저 코드나 git 에 넣음(PJ1-4) → `.env.local` 에 두고 서버(Route Handler)에서만 써요
- 원본 캡처를 배포 사이트에 넣음 → 캡처는 분석 문서와 발표 비교 자료로만 써요. 배포에는 자리 표시 사진
- 발표가 기능 자랑으로 끝남 → "문제 → 근거 → 해결" 순서로 바꾸고, 시연은 개선 포인트 흐름 하나를 끝까지
